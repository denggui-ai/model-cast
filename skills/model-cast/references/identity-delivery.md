# 身份资料交付与附件核对

在交付已确认人物、从资料库取图或准备下游身份附件时读取。独立 AI 使用与 Lookset 接入共享同一人物来源；商品保真仍由下游负责。

## 已有 01/04 的最小交付

用户要求交付已有身份资料，且 C4 的 01、04 均已获认可时，交付以下内容即可：

- 01 脸部正面、04 全身正面的原始文件副本，按字节复制，不重新生图、缩放或重编码。候选原图可另存为溯源，不冒充已定妆的 01/04。
- 一份简明说明：人物名称；已有选角依据及其来源；可见识别特点；01/04 的用途；独立 AI 与 Lookset 的取图方法；已确认、仅视觉判断和未验证事项。

从本人物 C4 的认可记录核对原件路径和哈希，再核对交付副本。不要仅凭目录名、人物名、最近一次任务或历史资料包选图。内部来源记录和哈希留在审计材料中，用户说明不用罗列技术字段。

这是一份通用身份资料，不是 C8 完整包、核心四图包或 Lookset D2 导出包。不要拿两张图伪填完整清单；`build_pack.py`、`check_pack.py` 和 D2 的现有契约不变。品牌/客群资料未留存时，只交付有来源的视觉选择理由并注明未知；不要为已采用的人物重选角，也不要事后编造商业依据。

完成标准：原件与认可记录对应，副本字节一致，说明和文件名可正确取用；状态写“最小身份资料已整理，待用户验收”，用户认可后写“最小身份资料已交付”。不据此标记 `gate2_pass`、`gate4_pass` 或真实复用通过。

## 实际请求前核对

以 C4 认可记录指定的原件建立或复用 [schema 1 身份锁](identity-lock.example.json)，存于当前 RUN 的 `c4/identity-lock.json` 或既有位置。`face01`/`body04` 保存原件绝对路径和实际哈希；两处记忆点采用已有选中记录，缺失时仅补有图像依据、注明为 AI 观察的描述。不能把待查附件的哈希反向填进锁里来让检查通过。

先从任务提示词确定哪些附件位置是 01 和 04，再检查**将实际发送的参数**，不要只检查另写的清单。对使用 `referenced_image_paths` 的原生请求，在宿主发送前运行：

```bash
python3 -B scripts/check_identity_refs.py --identity-lock /absolute/RUN/c4/identity-lock.json --request /absolute/task/request.json --face-index 2 --body-index 3
```

索引从 1 开始。上例表示“商品图、01、04”；若顺序是“01、04、商品图”，使用 `--face-index 1 --body-index 2`。脚本只读，核对两个指定身份位与已认可原件的字节；允许同字节副本与不同文件名，拒绝错人物、原件/副本变化、缺文件、无效索引和“最近几张图”引用。退出 0 表示本次来源核对通过；1 表示哈希错配；2 表示输入不能核对。非 0 时停止发送，纠正取图来源，不改写旧请求、旧回执或旧成片。

检查通过后按同一参数发送；复制、改名、修改附件或参数后须重新核对。其余附件由宿主确认仅是本任务商品或明确需要的辅助材料，不能混入另一人物身份。脚本不识别图片内容，也不解析提示词中的角色语义；索引和批准来源必须由宿主正确指定。

本脚本只覆盖 01+04 双图的原生请求。`gen_request.py` 生成的 CLI 请求或只用 01 的任务，宿主按相同原件基准核对真实 `-i` 参数/实际附件；不能把它们改写成虚拟原生请求后声称原执行入口已通过检查。已有 C6 身份锁校验保持不变。

## 两种使用方式与证据边界

- **独立 AI：**上传 01、04 与本次商品图，说明前两张固定人物、商品图固定商品。只需脸部参考时可用 01；无法确认宿主支持图片参考或图片实际进入工具时，标“未验证”，必要时请用户直接补传。
- **Lookset：**从同一份已确认 01/04 取图，按当前宿主支持的显式身份参考入口附上；准备请求时做上述核对。最小资料不冒充 D2；若该宿主只接受完整 D2，则如实记录此入口未交付，不自动扩图库或改 Schema。

来源核对通过不等于已发送、已生成或人物仍可辨认。只有实际附件、工具执行记录、真实输出与 Owner 对人物的判断相互对应，才记录该任务的身份复用结果。输入错配时保留 Owner 对成片的原话，但正确人物原件的复用仍是“未验证”；商品 QA 另记，不据此撤销已认可的 C4 身份。
